# ADR 0020: Use random opaque entity identities and optional English aliases

Status: Accepted

## Context

ADR 0015 made Concept and Card IDs readable by deriving them from English names, Concept IDs, and Card types. That coupled presentation, translation, file allocation, and durable identity. It also made `englishName` mandatory for non-English Concepts even when a learner did not need bilingual display, increased AI schema complexity, and caused avoidable failures with inexpensive models.

Mneme is a focused lifelong-learning plugin. Its durable identifiers need to be stable and collision-resistant, not meaningful to a reader. Titles, aliases, paths, Card fronts, and Card types are presentation or learning content and must be editable without participating in identity.

## Decision

- New Concept IDs are generated by Mneme as `concept-<8 random characters>`, using a lowercase ambiguity-resistant alphabet. New Card IDs use the same policy as `card-<8 random characters>`.
- IDs are immutable, program-owned, and semantically opaque. AI providers and editable title fields never create them.
- Concept Title, English Alias, Markdown path, Concept ID, and Card ID are independent values.
- A path collision may add a numeric suffix to the new file path or Card Group locator. It must not change Concept Title or either entity ID.
- An ID collision causes Mneme to generate another random ID. It must not add a semantic or numeric suffix derived from a title.
- `mneme_english_name` is redefined as an optional English Alias for display and search. It never supplies an identity stem.
- `Suggest English aliases` is a setting and defaults to off. When off, Concept-capture and Merge AI schemas omit `englishName`, and manual/review editors hide the field. When on, Mneme may request or accept a Latin-script alias for a non-English title. An English title does not show a redundant alias field.
- Existing valid readable Concept and Card IDs remain valid and immutable. Mneme performs no destructive migration. Existing stored aliases also remain readable.

## Consequences

- Renaming, translating, merging, or moving a Concept cannot imply an identity rewrite.
- Card Type and Concept ownership no longer leak into Card identity.
- Cheap AI providers handle a smaller default schema and no longer need to translate every Concept title.
- Markdown IDs are less mnemonic, so user-facing surfaces lead with Concept titles and Card fronts. IDs remain available for diagnostics and repair.
- Same-title Concepts can coexist with independent IDs. Exact title, alias, and path checks remain review signals, while identity allocation is handled separately.
- ADR 0015 remains as historical context but no longer governs new identity allocation or English Alias requirements.

## ID repair safeguards (2026-09-09)

Explicit repair of missing or duplicate IDs changes only the identity value. Existing Card type/custom attributes, YAML quotes/comments, surrounding content, and line endings must survive. Ambiguous ID syntax must block repair rather than select an arbitrary value.

Before changing a linked Card Group's Concept ID, repair checks fresh Markdown identities and links. Another Concept's owner, a shared Card Group link (including a legacy folder reference), a newly occupied ID, or a changed target link blocks all writes. A missing-ID Concept may adopt an unclaimed Card Group identity. Ordinary renaming still never rewrites IDs.

These are content and ownership preconditions. The current repair modals still use whole-file writes and compensation around state-migration callbacks; durable recovery, atomic ID reservations, and concurrent-write protection require a separate coordinator.
